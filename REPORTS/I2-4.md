## OPEN-I2-2 — (b) with (c)'s counter, landed

> **Correcting a precondition is not the same act as loosening an assertion**, and this record
> says which one it is in those words, because the diff will look similar later.

`sameDurableState` is **untouched**. It still demands exact equality and still catches a
*different* entry at a recorded index — the failure it exists for. What changed is when it is
entitled to run:

```go
durable := n.db.DurableSeq()
if n.db.visibleSeq() == durable && n.ackedSeq == durable && len(n.pending) == 0 {
```

| conjunct | side | says |
|---|---|---|
| `visibleSeq() == durable` | engine | nothing applied is still unsynced |
| `ackedSeq == durable` | driver | the fold has reached the engine's durable point |
| `len(pending) == 0` | driver | nothing this replica knows about is unaccounted for |

**Measured, not asserted.** 30 seeds of the A7 shape on `engine/model`, old guard vs new:

```
old:  75,630 comparisons, 218,596 declined
new:  75,630 comparisons, 218,596 declined
```

**Identical.** The added conjuncts cost nothing where the premise is true — which is what a
corrected precondition should look like, and the reason to measure rather than claim it.

**(c)'s counter is attached.** `DurabilityCrossChecksDeclined` surfaces through `store.Node` and
`RaftResult`, quoted beside the comparisons. `TestDurableRecordAgreesWithTheEngine` asserts the
comparison count **non-zero on `engine/model`**, where the premise holds, so a regression that
silenced the check everywhere fails rather than passes quietly.

*(That test mislabelled its own seed count — printing the constant 300 while `RAFT_SEEDS` bounded
it to 30. Fourth instance of a label that stopped describing its subject. Fixed.)*

### What the numbers say, stated plainly

**`drift=0.00` under chaos is the finding.** Throughput in the last third of the window was
**zero**. The cluster does not recover after a leader kill on the C++ engine within the run — T1,
T2 and T3 are three views of that one fact, not three independent failures.

**And nothing in the tree gates that** (GF-64). It surfaced here only because §3.2 declared a
recovery threshold in advance; the safety oracles are green over the same run, correctly, because
a cluster that stops serving has violated nothing.

**Two more honest observations:**
- Steady state on `engine/riftcgo` is **119 ops/s, p50 67ms** against **~940 ops/s, p50 8ms** on
  `engine/model`. That is the real engine's cost and it is not a defect; it is the first
  measurement of it under this workload.
- **`ledger=on` and `ledger=OFF` are indistinguishable here** — 37 ops/s both. BUG-055's oracle
  cost is real and was measured at 875 B/op, but against a C++ engine doing real fsyncs it is not
  the bottleneck. The two configurations are still reported separately, because which one
  produced a number is not something a reader should have to infer.
