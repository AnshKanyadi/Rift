## What is retracted

**Three chaos greens are withdrawn as safety evidence.** Runs of 2731, 2461 and 23,010
operations, each reported as "linearizability green, 3 leader kills of 3".

They are withdrawn for **two independent reasons**, and both matter:

1. **Every restart in them was an amnesiac node** (BUG-056). `engine/model` is purely
   in-memory and `store/` persists HardState and log *into* the engine, so a SIGKILLed
   `riftnode` came back with no term, no vote and no log — a fresh node wearing an existing
   identity. They passed because the amnesiac happened not to cast a second vote in a term it
   had already voted in. The fourth run is what happens when it does.

2. **The kill figures came from a counter now known to over-report** (BUG-058).
   `LeaderKills` was incremented on *intent*, before `Kill` was called, and `Kill` returns
   without signalling when the node is already down. **How many leaders those runs killed is
   not known.** "3 of 3" is an upper bound on a number nobody measured.

> Recording only the first reason would have preserved a false precision inside a retraction,
> which is a particularly bad place for one: a retraction is read as the careful version.

**What survives:** the transport, the client wire protocol, the correlation counters, the
process supervision, and the reality counters. The word *linearizable* does not.

**A fourth claim is also withdrawn:** that the `rift_cgo` build "does not link on this
machine" (BUG-057). It links. The archives were in the tree, built, 7.7 MB.

## What was built

### The client protocol — the last seam

```
request   op(1) seq(8) klen(4) key vlen(4) value
response  seq(8) status(1) vlen(4) value
```

Opcodes and statuses start at 1, so a zero byte is never valid. **Every refusal induced from
hand-built bytes before any writer existed** — nine of them, plus one that did not fire and
became GF-56.

**Correlation**, with the two cases that are not the happy path:

| class | disposition |
|---|---|
| unissued | LOUD, and it **gates** — a statement about the record, not the cluster |
| conflicting | LOUD — two different answers to one request, which porcupine never sees |
| duplicate | counted; wire weather |
| late-after-timeout | counted separately; `RespTimeout` subsumes any later answer |

The first response decides. Records are never reaped, so a forgotten operation cannot turn a
duplicate into a fabrication.

### The ledger is optional, on three conditions

- **Default on, absence as a decision.** `Config.Unobserved` must say so; a config that omits
  the ledger fails, and one that sets both fails. "I forgot" and "I meant it" must not produce
  the same program.
- **Real mode names its choice**, on the engine's own line: `ledger=on` /
  `ledger=OFF (--unobserved: NOT producing checker evidence)`. The gate refuses verdicts from
  an unobserved cluster.
- **The ledger does not change the run**, asserted over 64 seeds: byte-identical trace hashes
  *and* identical histories, with rebalance off.

### The measured limit of "byte-identical"

`sim.Trace.Step` folds `(step, at, kind, node, payloadLen)` — not payload content.

| instrument | catches | misses |
|---|---|---|
| trace hash | event shape | anything inside a payload that keeps its length |
| history comparison | client-visible values | anything that never reaches a client |
| both | the above | internal state reaching neither |

Two plants set the boundary: a dropped message **failed** on seed 0; an extra `hlc.Now()`
**passed both**, correctly, because it changes nothing a client can observe.
