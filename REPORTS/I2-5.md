# I2-5 — BUG-060: the cluster could not re-elect, and no oracle could see it

Session report. Follows `REPORTS/I2-4.md`.

---

## The diagnosis

T1, T2 and T3 shared one cause, as expected. Diagnosis before fixing, by measurement:

**Step 1 — arithmetic on the existing numbers.** `ok=1172` over a 30s window ≈ 10s × 119 ops/s.
The cluster served at full rate until the first kill and produced almost nothing after.

**Step 2 — per-second per-node counters across one kill.** `ldr=0 led=0` on all three nodes for
14 seconds while ticks advanced normally, bytes flowed, and requests were admitted.
**Not engine recovery, not the driver, not transport reconnect.**

**Step 3 — raft state per node.** Added `role/term/vote/last/commit` to the counters line:

```
t= 6s   n1[follower t=2 vote=1 last=575] n2[follower t=2 vote=3] n3[leader t=2 vote=3]
>>> killing leader node 3
t= 7s   n1[follower t=2 ...] n2[follower t=2 ...] n3[follower t=2 ...]
 ...
t=20s   n1[follower t=2 ...] n2[follower t=2 ...] n3[follower t=2 ...]
```

**All three stay `follower` at `term=2` forever.** The term never moves, so pre-vote rounds are
firing and never granting.

## BUG-060 — a pre-candidate kept naming the dead leader

`stepPreVote` refuses a round when:

```go
r.leader != 0 && r.electionElapsed < r.randomizedElectionTimeout
```

— *"I have heard from a leader inside one election timeout."* That refusal is correct: it stops a
node that can send but not receive from disrupting a healthy cluster.

**`preCampaign` reset `electionElapsed` without clearing `r.leader`.**

> After that reset the pair reads as *"I heard from the leader recently"* when what actually
> happened is **"I campaigned recently"** — and `r.leader` still names the node that just died,
> because nothing else clears it.

Three followers, each resetting its own timer on its own campaign, each therefore inside its own
window when its peers' pre-votes arrived. **Every node refused every pre-vote.** No quorum, no
term bump, no leader, indefinitely. `forceCampaign` already clears `r.leader` — and a node only
reaches `forceCampaign` by winning a pre-vote round, which is exactly what this made impossible.

**Fix: one line, `r.leader = 0` in `preCampaign`.** Two regression tests in `raft/`, both induced
(restoring the defect fails both).

### Why eight phases of simulation did not find it

**Nothing in this tree gates liveness** — GF-64, recorded one session earlier, demonstrating
itself immediately. The safety oracles ask whether a *wrong* thing happened; a cluster that
elects nobody does no wrong thing. The linearizability checker is green over a history in which
every operation timed out, because a timeout is *"may or may not have happened"* and every one
of them may not have.

> The defect was visible only as **a number nobody was comparing to anything**, and it became
> visible the moment §3.2 required a recovery threshold to be declared in advance.

Second time this session a declared-in-advance threshold found what no checker did — and the
first time it found a defect in the **system** rather than in the harness.

### One harness artifact it exposed

The kill ticker fired at `K`, `2K`, `3K` while the window *was* `3K`, so the last kill landed on
the boundary: `RecoveryAfter` found no slices past it and reported *"never recovered"*, which read
as a defect. **A kill the window cannot observe recovering is not a kill the run can measure** —
the schedule now stops rather than the measurement being excused.

## BENCHMARKS.md

The I2 section is in, with methodology, provenance, and what the numbers are not. Steady state is
reported as a **range across three runs (97–119 ops/s, p50 66.9–81.8ms)** rather than a best,
because run-to-run variance on a shared laptop is real and one run would imply a precision this
does not have.

`engine/model` under the identical harness is ~940 ops/s / p50 8ms. That ratio is **the real
engine's cost, measured for the first time** — not a defect, not a regression against anything,
since there is no prior number for this configuration.
